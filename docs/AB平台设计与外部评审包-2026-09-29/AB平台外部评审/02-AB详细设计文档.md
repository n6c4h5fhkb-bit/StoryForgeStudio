# A/B 精品创作平台：当前实现与详细设计

文档版本：1.0｜代码审阅日期：2026-09-29｜用途：外部架构评估与优化建议

本文件描述当前工作区的实际实现，并单独列出产品目标、尚未完成的设计和验证边界。它不是把此前计划重新包装成已交付能力。源码定位、文件指纹、完整路由和测试入口见同目录的 `04-代码与接口索引.md`、`05-代码快照索引.json`。

## 1. 产品目标、约束与成熟度

### 1.1 产品定位

System A（StoryLab）负责原创故事和小说改编，产出用户采用的故事剧本。System B（FrameLab）在该故事上再做影视化转换，产出用户采用的拍摄版，再组织导演分镜、资产、图片视频制作、审片和制作包。

精品质量与费用平衡是共同目标。用户希望 AI 主动完成分析、创作、检查和下一步准备，自己主要阅读、比较、提出修改、采用结果。流程应保留关键创作选择，同时避免逐个内部节点点击。

两条主要业务路线：

| 路线 | A 的任务 | B 的任务 | 质量判断重点 |
|---|---|---|---|
| 原创精品 | 选题、人物欲望、冲突、主动选择、因果和故事剧本 | 电影／剧集／短剧呈现转换与制作 | 故事成立、人物可信、视听表达有设计 |
| 小说推文短剧 | 根据指定原文范围改编，保留主要事实和证据 | 快节奏短剧，默认配置可用 Seedance 2.0 Fast 降低视频成本 | 尽早进入冲突、信息推进、情绪兑现、段尾吸引力和道具连续性 |

原创／小说改编是来源选择；电影／剧集／快节奏短剧是呈现选择；画幅是独立制作参数。小说推文也可以是有表演和对白的短剧，不等同于旁白配图。

### 1.2 固定约束

- A/B 独立运行、独立数据，通过文件交接；不是共享业务数据库。
- 不强制起步填写片长，不以固定分钟数、镜头数或反转间隔代替导演判断。
- 允许多轮候选与局部修改；AI 通过不等于用户已经采用。
- 正式采用稿、事件状态和素材记录由程序保存；会话历史不是正式事实库。
- 付费媒体每批先预览任务、参考和费用，再确认执行；不自动进行付费重试。
- 配音、字幕和最终剪辑主要在外部软件完成；B 保留旧装配器兼容与粗剪能力。
- 当前部署目标是单用户本地工作站，不是公网多租户服务。

### 1.3 当前成熟度的准确表述

当前是已有可运行流程、持久化、自动化测试和少量真实文字试跑的本地源码版本。不能据此认定所有完整版本目标已经验收，或真实成片稳定达到精品。

| 证据层 | 当前能证明什么 | 不能据此证明什么 |
|---|---|---|
| 代码静态审阅 | 模块、路由、数据字段、检查和控制路径存在 | 每种业务组合在真实环境都正确 |
| 自动化回归 | 测试范围内结构、恢复、缓存、连续性成立 | 未声明事实、审美和真实视频效果 |
| 离线界面／演示流程 | 能完成指定交互和交接 | 演示媒体具有真实人物表演质量 |
| 小范围真实文字 | 部分模型调用、会话续接、修改和独立审查有效 | 全部长篇、多日调用及所有模型都稳定 |
| 真实媒体 | 需要另行批次试跑和人工判断 | 当前没有完整付费媒体质量验收 |

发布清单记录 A 164 项、B 218 项测试，历史浏览器证据包含桌面与 390px 窄屏。本次文档工作没有重新运行全部业务测试。清单中的 `paidProvidersLiveVerified=false` 必须保留；历史界面通过不能替代最近修改后的界面复验。

## 2. 系统架构与部署

### 2.1 运行架构

```text
用户浏览器
├─ System A / 默认 127.0.0.1:8787
│  ├─ 阅读界面、候选比较、自然语言修改、反馈与记忆
│  ├─ FastAPI → StoryService / NovelService / IdeationService
│  ├─ Store + Jobs + LLM + ExperienceService
│  └─ 自己的 data/studio.sqlite3、settings.json、media、exports
│
├─ SceneExport-v1 / schemaVersion:4 文件
│  └─ 只交接采用故事与版本化依据
│
└─ System B / 默认 127.0.0.1:8788
   ├─ 拍摄稿、拍法、分镜、素材、生成与审片界面
   ├─ FastAPI → ProductionService + ShootingWorkflow + ProposalWorkflow
   ├─ Store + Jobs + LLM + ExperienceService
   ├─ RunnerRegistry → 媒体 Provider / Dreamina CLI / 手工导入
   ├─ Gates / FFmpeg / Assembly / 制作包导出
   └─ 自己的 data/studio.sqlite3、settings.json、media、exports

文字调用：A/B → 各自 LLM 适配器 → 同账号调用队列 → 本地 Codex CLI
其他文字配置：可选 OpenAI / Anthropic / Gemini API / demo
媒体调用：B 的独立执行记录与费用预览，不由文字会话自行触发
```

Python 最低版本在清单中为 3.11，后端 FastAPI，校验使用 Pydantic／JSON Schema，数据使用 SQLite WAL。前端为本地静态 HTML/CSS/JavaScript，包含阅读界面与升级层。任务用线程池执行，`Jobs` 默认 3 个工作线程；这不等于允许同时提交 3 个 Codex 请求。

两个平台分别打包基础模块，包括 `core.py`、`llm.py`、`codex_cli.py`、`story_contract.py`、`experience.py` 等。这样可独立分发，但也增加两份实现漂移的维护风险，需要契约测试与同步检查。

### 2.2 数据目录和基础设施

| 内容 | A/B 项目内 | 账号级共享 |
|---|---|---|
| 正式作品、候选、素材对象 | 各自 SQLite documents | 无 |
| 审计和 UI 事件 | operations / events | 无 |
| 后台任务与去重 | jobs / job_idempotency | 无 |
| 结果缓存和重定向 | cache / redirects | 无 |
| Codex 职责会话记录 | 各自 `codex_session` 文档 | CLI 历史由所用登录目录管理 |
| 媒体和工作目录 | 各自 data/media、codex-workspaces | 无 |
| 调用协调 | 平台请求进入队列 | `<CodexHome>/story-studio/call-queue.sqlite3` |

项目的 `_version` 是乐观并发版本；`digest` 是规范化 JSON 的 SHA-256；这些与作品采用版本、文件 SHA-256、会话输入指纹各有用途，不能互相替代。

## 3. 用户完整流程与自动推进

```text
A：原创选题 / 导入小说全本
→ 确定本轮目标（原创阶段 / 小说选定章节）
→ AI 候选 → 程序检查 → 独立审查 → 有界局部返修
→ 用户阅读、采用或提出修改
→ A 导出采用故事 SceneExport v4

B：导入 A → 选择电影 / 剧集 / 快节奏短剧
→ 生成完整拍摄版、改动依据和来源映射
→ 程序检查 + 独立审查
→ 用户预览影响并采用
→ 提取事件素材需求
→ 关键场次比较拍法；普通场次推进推荐稿
→ 整场导演与分镜 → 按实际入画对象核对参考
→ 确定生成单元 → 批次 dry-run → 用户确认
→ 执行／恢复 → 真实文件初筛 → 用户审片和采用区间
→ 局部返修或导出制作包 → 外部最终剪辑
```

这里的“自动”是程序安排授权范围内的下一任务。它不会自动替用户采纳核心故事方向，不会让模型自由扩张任务，也不会越过媒体费用确认。

### 3.1 必要选择点

| 选择点 | 用户看到什么 | 后台处理什么 |
|---|---|---|
| 原创方向／故事候选 | 完整推荐内容与关键备选 | 候选通道、结构检查、质量复核、差异 |
| 小说本轮改编 | 选段改编稿、问题位置、来源范围 | 原文定位、相关前情、事件校验、独立审查 |
| B 拍摄版 | 可读完整稿、改动理由、事实修改提案 | 模式转换、映射、覆盖、版本影响 |
| 关键场次拍法 | 有实质差异的观看重点、调度、切点与声音 | 生成整场导演方案和镜头，分别检查 |
| 素材与付费批次 | 真实参考、缺项、任务、已知／未知价格 | 编译提示词、依赖排序、缓存和能力校验 |
| 媒体采用 | 候选文件、观察、实际区间与末态 | 初筛、证据抽帧、依赖失效与文件归档 |
| 跨作品经验 | 规则、范围、例外与范例 | 当前作品记录、适用筛选、应用记录 |

### 3.2 状态机

工作流状态包含 `ready`、`awaiting_choice`、`needs_attention`、`complete`。后台作业状态包含 `queued`、`running`、`succeeded`、`failed`、`cancelled`、`interrupted`。候选通常包含 `proposed`、`adopted`、`rejected`；正式对象另有 `draft`、`accepted`、`locked`、`archived` 和 freshness。

候选 `passed=true` 表示当前检查通过，`status=adopted` 表示用户采用。任务 `succeeded` 也可能只代表成功生成了需要选择或处理的候选，不能直接表示作品完成。

`/advance` 是有界工作流推进，不是自由 Agent 循环。A 原创通常推进到下一批候选；A 小说直接处理指定段；B 的新流程可连续整理素材和推进普通场次，遇到关键拍法或必要问题停止。B 保留 `single/until_choice` 兼容，同时使用独立 `presentationMode`，防止将“推进方式”误认为“影视方向”。

## 4. System A：原创设计

### 4.1 故事层级与契约

A 有两种层级：简化模式使用 `premise → sequence → scene → script`；完整模式为 `premise → spine → sequence → scene → script`。场景正文中可包含 beats，但它不是当前顶层节点层级。阅读界面可以降低操作密度，内部仍保存节点、父子关系、顺序和约束。

节点契约描述：概要、前置条件、后置条件、价值变化、揭示、后续义务、相关实体。正文、契约与采用修订分别记录。正式 canon 保存人物／地点／道具、事实和人物信念；叙事边描述信息和因果关联。

顺序使用有理数索引，插入时不必全量重排同级节点。节点有当前修订指针、锁定和新鲜度；分支、恢复、撤销和结构操作保留历史。

### 4.2 原创流程

1. 可从 AI 选题卡开始，也可直接输入故事种子、类型和语气。
2. 主控读取采用方向、约束、父级契约、邻近场景、相关 canon 与适用经验。
3. 按任务策略生成候选；不同策略可复用各自职责会话。
4. 程序检查结构和硬约束；独立审查者检查来源、因果、对白、事件、连续性、呈现，评价质量与实质差异。
5. 仅返修未通过且仍有修复额度的候选；未变且已通过的候选复用有效审查。
6. 用户采用候选。候选提出的实体、事实或信念变更按确认路径进入正式设定。
7. 逐层展开到正文，通读、局部修改、扫描，再导出。

原创上下文组织在 `StoryService.context()`：固定约束、故事设定、祖先、邻居、canon、叙事边、经验和当前任务。超过字符限制时先减少邻居正文；必要约束仍过大则明确阻止提交。它是程序范围筛选，不是成熟的语义检索系统。

### 4.3 修改与影响

支持填充、变体、改写、深化、拆分、合并、插入、移动揭示和结构操作。部分操作需要 `planHash` 绑定最新影响预览。锁定节点不被普通改写覆盖；受影响对象通过 freshness 和问题记录提示处理。

这一设计可以保存采用内容，但仍需评估：故事状态能否在每个原创路径中完整结构化。目前原创导出的 `storyDocument` 使用保守构造，并不等同于小说路径已经生成的详细事件账本；B 可能需要补全连续性。

## 5. System A：小说全本、指定范围与续写

### 5.1 原文载入不等于全部理解

支持 TXT 和粘贴正文，前端尝试 UTF-8，失败后尝试 GB18030；后端统一换行，保存全本正文、SHA-256、来源名称和章节索引，正文上限为 100 MiB。

当前默认行为是：**保存全本 → 建立索引 → 只处理本轮指定章节 → 产生改编候选**。显式“全书深读”是另一任务，不是前几章改编的前置门槛。

| 层级 | 保存内容 | 是否说明已理解 |
|---|---|---|
| 原文已保存 | `novel_source.text/sha256` | 否 |
| 索引已建立 | 章节名称、字符起止、阅读单元 ID | 否 |
| 已载入模型任务 | `readRanges` 与实际选段 | 只证明载入记录，须结合调用和审查 |
| 通过改编审查 | `chapter_analysis`、`analysisRanges`、用途标记 | 证明该范围的改编检查，不等同于全书分析 |
| 专项逐段深读 | `book_unit_analysis` | 对应该阅读单元的分析结论 |
| 汇总完成 | `book_analysis` | 当前代码根据覆盖形成汇总，仍需检查结论充分性 |

章节解析版本 `CHAPTER_INDEX_VERSION=2` 已处理连续重复章节标题，避免把标题双写误计为两章；缺少采用稿及历史候选的旧来源可安全重建索引，已有历史记录不会直接改编号。

长章可切为多个阅读单元：`number` 代表单元序号，`chapterNumber` 可代表原章节号。因此 UI 的“第 1–5 个章节单元”未必总等于原书第 1–5 章。此语义仍值得专门评估与改进。

### 5.2 指定范围改编

```text
start/end 选择阅读单元
→ 校验范围与选段长度（当前单次原文 ≤80,000 字符）
→ 保存 readRange 载入凭据
→ 使用已存在的全书／部分分析，不额外等待全本深读
→ 带入相关实体、入场状态、必要前情和当前经验
→ 生成完整候选及事件状态
→ 程序校验 → 独立复核 → 最多两轮自动修订
→ 保存 proposed 候选，用户采用后才写入正式故事
```

直接改编可以同时形成经审查的范围摘要；当前代码没有保证每次先单独完成“分析 Agent”，再调用改编 Agent。对外描述必须区分“分析和改编合并完成”与“专项深读”。

连续改编由 `activeNovelDraft` 和 `nextChapter` 管理。续写携带相关旧实体和上一段末态，生成新段后合并到采用稿；程序保护旧场次、已有身份及已知容器内容，禁止凭空加入物品或重复旧场次 ID。

局部修订指定 `sceneIds`。其他采用场次受到保护。失败候选可传 `repairDraftId`，绑定原来源、阅读范围和采用基稿，以 JSON Patch 修复，不再从零重写；新结果保存 `repairedFrom`。

### 5.3 可选全书深读

`analyze_all()` 按阅读单元执行，保存摘要、人物、关系、时间线、伏笔、物件、规则、保护事实、改编机会和不确定项。未变的单元可按 `unitHash` 复用，任务可在中断后接着处理未完成单元。

当前分析模型接收本单元原文和上一单元摘要；汇总主要用字段去重合并。尚未看到独立的全书综合推理／一致性审查环节。因此不能声称已有完备的全书关系推导、跨章伏笔解释与检索体系。原文更新复用内容相同单元时，也需评估前情变化是否改变解释。

### 5.4 阅读进度事故与现有修复

此前“上传全本、选择前 1–5 章”触发了强制全本分析，加上重复标题索引，把本来小范围任务扩大为数百单元；另外候选较长时，返修和审查资料超出了原 32,000 字符应用限制。通用 Jobs 的初始进度 `.02` 不是模型已处理 2% 的证据。

当前已改为指定范围优先、全书深读独立，并加入失败候选局部修复；`GPT-5.6 Sol · High` 的界面预设为 600 秒、96,000 字符。该字符值是应用提交资料限制，不是模型 token 窗口。

同一全本的前 1–5 章真实试跑已形成通过审查、等待用户选择的候选，但这不能证明所有长文本场景已解决。超大范围自动拆任务、完整上下文占用测算和连续进度显示仍需外部评估。

## 6. A → B 交接协议

使用 `format: SceneExport-v1`，当前 `schemaVersion:4`。B 新导入路径读取版本 1–4；旧工作流还有兼容导入路径。

| 字段组 | 作用 |
|---|---|
| project / source | 作品、来源路线、来源指纹、原文定位与采用稿 |
| scenes | 正文、稳定正文块／对白 ID、节点修订、契约和相关设定 |
| storyDocument | 可回放事件、实体、初始状态和播放计划 |
| analysisCoverage | 载入与分析范围、用途、全书完成状态 |
| knowledgeSnapshot | 正式事实、信念、各场知情起态与变化 |
| dramaticFunctions | 价值变化、揭示和后续义务 |
| evidenceSnapshot | 来源指纹和场次修订依据 |
| versionFingerprint | 本次交接内容的版本指纹 |

小说采用稿导出时会校验节点正文与采用文档一致；若在其他入口改了正文但没有重新经过小说复核，会拒绝将两套不同依据混成同一交接。

B 保存导入来源历史；导入新版 A 文件不会立即覆盖已有制作结果。先生成新拍摄稿，展示差异和影响，再采用。旧版缺少连续性时标记待补全，不能假装已经有完整事件证据。

协议指纹用于内容一致性，不是数字签名或授权凭证。外部评审应检查导入校验覆盖、知识模型表达能力，以及稳定 ID 在删改、合并、重排后的行为。

## 7. System B：二次影视化转换

### 7.1 转换方向

| mode | 创作重点 | 不能自动改变的内容 |
|---|---|---|
| cinema / 电影 | 场面、视觉叙事、潜台词、铺垫、留白与节奏反差 | 人物身份、关键动机、规则、重大因果和结果 |
| series / 剧集 | 关系推进、持续情节、场次组织和承接 | 同上 |
| fast_drama / 快节奏短剧 | 冲突进入、信息揭示、对白密度、情绪兑现和段尾吸引力 | 同上 |

B 可以压缩、改写、合并对白，外化心理、改场次、调整观看顺序。受保护事实变动必须声明为 `storyChanges`；当前采用路径遇到此字段会阻止采用，并要求先到 A 确认故事新版本。它不是已完成的“一键跨平台事实修改协同”。隐瞒变动仍依赖独立语义审查发现。

### 7.2 拍摄版对象

`shooting_script` 保存来源快照、sourceHash、mode、完整 payload、sourceMapping、改动理由、storyChanges、复核尝试、passed、status、baseShootingId 和 requestKey。

每个原稿正文块都必须有来源映射：保留／删除／合并／改写 → 目标块 ID → 理由。映射要覆盖所有原块和新块，避免悄悄丢掉对白信息或添加没有依据的新内容；程序只能检查引用和覆盖，戏剧功能是否保留由审查者判断。

采用预览返回 changed/preserved 场次、受影响镜头／素材数、故事变动、候选版本、来源和 `planHash`。采用时再次校验计划与当前来源。

### 7.3 当前“多方向版本”的实际边界

电影、剧集、短剧候选分别保存，CLI 转换会话也按方向隔离。**但是同一 B 项目目前只有一个 `activeShootingId`，采用时更新同一组活动 scene/direction/shot 对象。**

因此当前支持“保留多方向拍摄稿历史、切换当前采用稿”，不能等同于“电影和短剧各自拥有同时存在、完全独立的活动素材、分镜、生成任务和采用指针”。采用旧拍摄稿可能重新更新／归档活动对象并使下游失效。

完整制作分支是待完善项。建议评估 `productionBranchId`、每分支采用指针、共享身份资产、方向专属状态／镜头／媒体的边界；在完成前，两个 B 项目分别制作可以提供明确隔离，但不是单项目内自动分支功能。

## 8. 事件、道具与知识连续性

### 8.1 数据模型

`continuity.entities` 保存实体身份和视觉状态键；`initialState` 保存所有实体初态；`events` 保存实际发生顺序。每个事件绑定场次、地点、参与者、动作、前置条件、`changes`、对白与原文依据。

`presentationPlan` 单独保存观众观看顺序，引用事件，声明 main／preview／flashback／time_jump、before／after、理由和对白分配。预演不改变故事初态；不能把播放顺序直接当作物理发生顺序。

### 8.2 物理状态表达

| 状态 | 例子 | 区分意义 |
|---|---|---|
| 开合 | `lid: closed/open` | 取放前需开盒；不能以闭盒图作为开盒后的可见内容 |
| 持有 | `pos: {rel: held_by, target: person_a}` | 道具交接有持有者与地点依据 |
| 包含 | `pos: {rel: inside, target: box}` | 移动盒子会带着内物移动，无需复制虚假位置 |
| 穿戴／附着 | worn_by / attached_to | 服装、饰物和伤势有归属 |
| 未知 | `{unknown:true}` | 尚不知道内容，不能解释为空 |
| 明确为空 | `contentsKnown:true`，无有效内物 | 开盒看到空与没有看到是不同信息 |
| 隐藏 | visibleTo / 闭合非透明容器 | 存在但当前观众看不到 |
| 损坏／消耗／销毁 | declared fields、destroyed/consumed/active | 销毁后不能继续持有或入画 |

`replay()` 对每个事件生成 before/after 状态。变化的 `from` 必须匹配上一状态；位置引用、包含循环、封闭容器取放、跨地点交接、销毁后出现等由程序检查。

### 8.3 检查层次

1. 程序：已声明实体、状态、引用、覆盖和顺序。
2. 独立文字审查：原文与事件账本是否一致，遗漏物件、因果与知情是否合理。
3. 真实媒体观察：画面中实际做了什么，与采用状态是否一致。

程序对已声明模型的验证很强，但不会从任意自然语言自动证明没有遗漏，也无法保证模型始终正确提取状态。人物知识／误信与观众知识已有交换快照和部分叙事检查，仍需评估是否足以覆盖复杂误导、倒叙和不可靠叙述。

## 9. 素材、身份和参考职责

### 9.1 三阶段素材治理

产品目标是“拍摄稿提取需求 → 粗分镜筛实际入画 → 正式分镜反查遗漏”。当前实现根据采用事件参与者和地点创建 master／variant，导演分镜按 references 表达入画对象，执行 manifest 检查实际参考。

不应把这些机制描述为已经存在一个独立、完整的“粗分镜 Agent”以及自动反查所有布景道具的语义扫描器。未进入事件登记的背景物件仍可能漏提，尤其是连续多个镜头出现但不参与因果的布景。

### 9.2 三层分离

| 层 | 保存什么 | 变更影响 |
|---|---|---|
| master | 稳定身份、形制、锚点、freezeString、identityHash | 身份变化影响相关变体与媒体 |
| variant | 服装、开合、损坏、可见内物等临时外观，claims/embedded | 只影响使用该状态的任务与强依赖 |
| file | 真实文件、路径、URL、大小、SHA-256 | 文件替换必须进入依赖和缓存校验 |

身份指纹包含实际视觉设定，不能只用角色姓名。默认身份图与状态图分开；状态变体用 claims 哈希复用相同状态，不为每个事件重复生成。

### 9.3 参考绑定

每项 references 表达 entity、role、phase、控制字段、excludeInheritance、claims、实际参考文件与 reviewEvidence。职责包含 identity、environment、start_state、end_state、detail。

身份图控制同一个人／物的外观，但不自动继承旧场景、姿势、服装和持有物；场景图控制空间，不夹带不属于当前事件的道具；end_state 不能伪装成 before 起态。

当前参考审查接口保存观察依据和职责；这不自动说明每张图都已被真实视觉模型检查。缺少真实检查时必须显示来源和人工依据。缺图只阻塞实际依赖它的任务。

## 10. 导演、关键拍法与分镜

### 10.1 内部创作顺序

导演先确定观看重点、情绪、镜头组、切点和声音策略，再细化调度、表演、摄影、灯光、构图与每镜信息承载。`SceneDirection` 描述整场基准，`ShotContract` 描述具体镜头。

每镜绑定 eventId、presentationId、eventPhase、dialogueIds、subjects、参考、时长、动作、声音和制作风险。提示词编译器忠实转写采用方案，不应该在生成阶段偷偷补写 A 已删除对白或新增剧情道具。

### 10.2 关键场次

当前 `key_scene_roles()` 使用位置和事件复杂度启发式：首场对应开场／人物亮相，末场对应高潮，中场或特殊播放对应揭示，参与者与变化较多场对应复杂调度。

这能减少逐场选择，但不等于已经具备成熟的语义导演选场能力。关键场提供至少两类有实质差异的拍法；普通场在新流程下可自动采用复核通过的推荐结果。外部应评估启发式是否漏掉真实反转／情绪高潮，以及自动采用普通场是否符合精品目标。

### 10.3 局部修改

已有镜头可选不连续、多场和锁定保护。局部修改要求恰好覆盖所选可修改镜头，保留 ID、当前时长、整场灯光／调度／色彩／声音和其他镜头。它适合定点精修，但也限制了局部修改时调整节奏、拆合镜头和镜长；更大的变化需要明确整场修订路径。

轴线、屏幕方向、人物左右等有模型字段和部分规则检查；自由文本调度还需要独立审查，不能宣称完整三维空间推理已经覆盖全部镜头。

## 11. 分镜与媒体生成单元

镜头是导演与剪辑表达；生成单元是实际供应商请求。多个连续镜头可以组成一个视频请求，避免每镜机械调用造成成本和动作断裂。

```text
采用镜头
→ 按连续性和目标编组
→ 每组：镜头顺序、累计时长、提示词、实际图序号
→ 去重参考文件，并保留各自职责
→ 绑定上游采用视频／末态
→ 根据配置／CLI 能力检查时长、图数、参考视频和承接方式
→ 保存 generation_task / inputHash
→ dry-run + planHash
→ 确认执行
→ 文件返回后等待各镜实际区间标定与审片
```

生成单元中会使用参考图真实索引编译每镜描述。外部强依赖等待上游视频采用，校验文件哈希、采用区间和观察末态；frame_chain 使用采用区间末态帧，extension/ref_video 使用实际采用区间。

目前有单镜 render 与新 generation-task 两套路径并存。它们在缓存、恢复、采用区间、运行中变更保护和费用规则上是否一致，是评审重点。

Seedance 模型限制由当前配置和 Dreamina CLI 帮助能力处理。本报告不写死供应商的当前秒数／图数上限。默认配置字段为 `videoModel=seedance2.0fast`、`videoResolution=720p`，不等于用户已启用 provider=dreamina 或所有设置都被供应商接受。

## 12. Agent 控制：主控、独立职责与执行权限

### 12.1 三种“Agent”必须区分

| 名称 | 当前实际含义 | 是否自主运行工具 |
|---|---|---|
| 项目主控 | 程序状态机、业务服务、任务队列和采用校验 | 由程序按受控路径调用 |
| 创作／复核 Agent | 不同职责、scope 和持久 CLI 会话中的模型推理 | 当前 Codex 文字适配器禁用工具与自主委派 |
| 媒体执行 Runner | 执行明确 TaskSpec 的本地进程／配置的第三方执行器 | 受白名单、路由、资格检查和工作目录约束 |

当前没有另付费的模型“总管”持续读取所有历史，也没有默认启动一堆会话窗口。职责会话在首次需要时创建，用户不用手动维护上下文。

### 12.2 会话树

```text
用户：采用、修改、费用确认
└─ 程序主控：以数据库正式版本安排任务
   ├─ A 项目 P_A
   │  ├─ 原创：目标节点 × 层级 × 阶段 × 策略
   │  │  └─ 独立 validator 复核会话
   │  ├─ novel-analysis:<sourceId>：显式全书逐段分析
   │  ├─ novel:<sourceId>：本书选段改编、续写、局部返修
   │  │  └─ review:novel:<sourceId>：独立来源与事件审查
   │  └─ 其他观察／扫描职责：按角色与目标隔离
   │
   └─ B 项目 P_B（导入采用文件，不继承 A 作者推理）
      ├─ shooting:cinema
      │  └─ review:shooting:cinema
      ├─ shooting:series
      │  └─ review:shooting:series
      ├─ shooting:fast_drama
      │  └─ review:shooting:fast_drama
      ├─ shots:<方向>:<sceneId>：本场导演、分镜与局部改动
      │  └─ review:shots:<方向>:<sceneId>
      └─ 媒体执行／观察：TaskSpec 或观察请求，独立于作者会话
```

树中 scope 还要与 project、role、连接身份一起确定唯一会话。B 三个方向仅在实际选择时创建；图中的会话独立不代表已实现三套完全独立制作数据库分支。

### 12.3 哪些地方需要独立 Agent

| 工作 | 当前实现 | 应独立的原因／评估建议 |
|---|---|---|
| 原创作者与审查者 | 作者角色与 validator 请求／会话隔离 | 防止作者自评；必要 |
| 小说改编与来源审查 | structure 与 reviewer，scope 分开 | 审原文、因果和状态，必要 |
| 全书分析与改编 | 两个明确 scope；分析非默认前置 | 任务和输出不同；专项分析按需 |
| 三种 B 转换方向 | treatment，按 mode 分会话 | 避免短剧偏好污染电影留白；必要 |
| B 转换与复核 | treatment 与 reviewer 分开 | 检查事实和呈现实际差异；必要 |
| 各场导演 | 按方向和场次续用 | 缩小上下文与返修范围；默认合理 |
| 导演与分镜复核 | shots 与 reviewer 分开 | 覆盖、对白、状态与轴线；必要 |
| 素材提取与资产程序 | 事件程序提取为主 | 不必每个物件一个 Agent；复杂遗漏可加专项审查 |
| 粗分镜与正式分镜 | 当前同一导演职责中完成 | 尚无独立粗分镜服务；是否分开需证明收益 |
| 审片与作者 | Gates／vision／检测器／人工观察 | 必须读真实文件，不能沿用作者自评 |
| 经验整理 | 当前规则记录和应用为主 | 批量整理可用单独会话；目前未见完整自动提炼服务 |
| 媒体执行 | trusted subprocess 默认；其他 runner 需资格 | 工具权限、费用和恢复隔离 |

“独立”主要指上下文、任务与判断隔离，不强制使用另一家公司模型。复核会话本身也续用，会保留之前审查历史；它不继承作者推理，但不等同于每轮完全无历史的盲审。外部应评估历史结论导致的锚定偏差。

### 12.4 主控决策边界

程序决定：下一步、依据版本、任务范围、适用经验、请求去重、缓存、工具允许项、费用计划、采用条件和失效传播。

模型决定：人物动机和因果表达、改编取舍、导演创作、质量判断与问题证据。模型返回候选 JSON／报告／补丁；不能自己把候选写成正式版本，也不能自行下单生成媒体。

用户决定：核心故事与拍摄版采用、关键拍法、授权事实变化、付费批次、媒体终选以及跨作品经验推广。

## 13. Codex CLI 会话、增量上下文与模型

### 13.1 连接和身份

文字调用通过本地 CLI `codex --no-daemon exec`，续接时使用明确 `resume <threadId>`，不用 `--last`，也不借用当前桌面开发聊天的 threadId。npm 启动器被解析到实际 Node 入口，参数通过数组传递，避免 shell 字符串插值。

适配器读取指定 CodexHome 的配置以解析默认模型、推理强度和认证存储，再用 `--ignore-user-config` 和显式受控覆盖执行。继承的是选定必要配置，不是把全局开发指令、插件或记忆带进剧本任务。

界面预设支持 `gpt-5.6-sol / high / timeout=600 / contextCharacters=96000`。模型字符串表示平台配置，不是对当前账号可用性的保证；连接检查和真实调用决定可用性。API temperature／maxTokens／extraBody 不被当作 CLI 的已生效参数。

会话身份包含 project、role、scope、协议、命令／登录目录、模型和推理强度等。结果缓存另包含实际 CLI 运行文件／版本和提示指令身份。程序允许提示措辞或 CLI 更新使结果缓存变化，同时尽量保留可兼容的职责会话；协议或模型变化可能分出新会话。

### 13.2 每次续接发送什么

| 场景 | 发送方式 | 保留什么 |
|---|---|---|
| 首次职责任务 | 完整 snapshot：rules、input、inputHash | 创建持久会话 |
| 同任务继续 | delta：baseHash、inputHash、add/replace/remove 补丁 | 同会话与未变资料 |
| 紧邻局部返修 | previousCandidate 精确匹配上一输出时，用 resultBinding | 不重复发送同一候选 |
| 大范围替换 | snapshot 比 delta 更短时发送 snapshot | 仍用同一会话 |
| 维护检查点 | 达 12 次 delta，或 ≥4 次且累计差异 >完整资料两倍 | 在下一正常调用同步状态，不额外总结调用 |
| 上次中断／上下文丢失 | needsResync → 完整 snapshot | 原会话可续则续；重同步有界 |
| 明确重置 | 清空会话绑定，后续重建 | 正式采用数据不因此删除 |

`studio-context-v1` 包含删除操作。经验撤销和素材删除不能只“追加一段新说明”，而要从当前有效输入中移除。程序用哈希核对模型响应所依据的输入；发现无法恢复输入时只允许原会话有界重同步，不能猜测缺失事实。

### 13.3 复核上下文

独立复核接收来源、约束、相关前情、候选和检查项。通常不携带作者生成过程、shapeExample、自评和随机候选标记；续写或局部修订保留必要采用片段。检查要求具体位置和依据，不接受只输出“通过”。

六类通用检查：source_fidelity、cause_effect、dialogue、event_coverage、continuity、presentation。报告格式不完整时修报告，不据此重写候选。

### 13.4 调用队列与取消

A/B 通过同一个 CodexHome 的跨进程 FIFO 队列协调平台调用，默认并发 1；各客户端配置不同限制时保守取值。队列只包含租约和进程元数据，不包含正文或密钥。

活进程不会仅因为长时间未更新就被抢占；死亡进程清理租约。职责会话也有持久 ownerPid 防止同时续接。Windows 进程树清理用于超时、取消和父进程退出。排队阶段可以取消。

队列不控制用户手动启动的 Codex CLI、桌面其他会话或其他应用，因此不是账号全部用量的统一配额系统。

### 13.5 缓存的三个层次

1. 业务候选复用：已存在、有效的本轮候选直接返回。
2. 平台结果缓存：实际请求指纹一致时不启动 CLI／媒体任务。
3. 供应商前缀缓存：由服务商决定，CLI 返回 cached_input_tokens 后记录。

同会话可以减少重复发送，但不保证每轮供应商命中，更不表示免费。历史小样证明续接和部分缓存有效，不足以承诺所有项目固定节省比例。

## 14. 有界审查与调用成本

普通 `generate_reviewed()` 最多首稿加 2 轮创作返修；指定失败基稿修复最多 2 轮补丁。补丁只允许有限 JSON Pointer add/replace/remove，合并后完整校验。无变化会停下并显示问题。

每次完整有效候选可触发独立审查，审查报告本身最多尝试 3 次格式修复。因而“最多两轮返修”不等于“整个任务最多两次模型调用”：最坏路径可有 3 次作者调用和至多 9 次审查请求，另有可能的上下文重同步。多数正常路径应是首稿＋一次审查，实际缓存命中减少调用。

原创多策略／多候选另有批次审查机制，不能套用同一固定次数。外部应基于真实 run 记录核算首轮采用率、无效格式率、平均修复次数、等待时间和被取消的已提交请求。

CLI 记录实际返回用量，并处理持续会话累计计数的差额，避免把历史累计 token 每轮重复计入。CLI 订阅用量不虚构为 API 美元价格；价格未知必须标记未知。API 价格和缓存输入价格根据配置记录，缺用量时保留估计标记。

A 现有设置保留 API 项目推理预算机制；B 设置移除旧累计预算帽，按批次媒体计划确认。没有新增媒体累计预算上限。外部优化应围绕更少无效调用与更少付费返工，而不是取消必要审查。

## 15. 缓存、依赖与采用影响

### 15.1 主要指纹

| 对象 | 当前关键依据 | 评审注意 |
|---|---|---|
| LLM 结果 | project、role、provider/model、system、user、schema、images、运行身份 | 适用经验进入 user 后能改变低层缓存 |
| 小说范围分析 | sourceHash、范围／单元内容 | 前情和规则改变是否需重评 |
| 拍摄版 | sourceHash、mode、instruction、目标场次、基稿、候选意图 | 高层 requestKey 与经验版本是否一致 |
| 导演稿 | shootingHash、style、身份、已有 shots，任务参数 | creative_snapshot 当前未显式包含经验版本 |
| 媒体结果 | 实际提示词、配置、身份／变体、文件、seed、尺寸、时长、强依赖 | 同一实际请求可复用，采用状态独立 |
| 生成单元 | 镜头编译结果、参考职责／签名、采用绑定、profile、focus、style | 改区间／末态应改变依赖签名 |
| 采用绑定 | fileHash、interval、observedEndState | 末态依据是否充分仍要真实观察 |

文件缓存检查实际文件存在及声明 SHA-256。替换文件不能仅保留 URL 就当作同一资产。

### 15.2 失效传播

```text
身份变更 → 相关状态变体 → 使用它的媒体
拍摄场次变更 → 本场方向／镜头／媒体
镜头变更 → 本镜媒体 + 强依赖后续
上游采用视频／区间／末态变更
  → frame_chain / extension / ref_video 后续递归失效
  → 相关生成单元失效
无依赖的场次与媒体保留
```

freshness 可表达 clean、opportunity、broken 等状态；失效不代表删除历史文件。Pin、锁定和仲裁保护用户采用结果，进一步返工需要说明影响。

不能把所有失效都声称是字段级最小传播：部分路径按场次或身份资产传播，可能偏保守；复杂依赖仍需要测试。运行中上游变化，新 generation-unit 路径返回后会重新计算 inputHash；旧单镜路径的返回后一致性保护需单独核对。

### 15.3 本次静态审阅发现的缓存风险

小说 propose 和拍摄版 propose 会先按高层 requestKey 返回已有 passed 候选，该 key 没有显式包含经验版本；导演快照／候选 key 同样未显式包含经验。低层 LLM 请求确实带经验，但若高层提前返回就不会进入低层检查。

因此“经验停用／修改后所有相关候选必然退出复用”目前不能下确定结论。应新增复现：先生成未采用候选 → 修改或撤销适用经验 → 同目标再次生成／采用 → 检查实际经验快照和失效。这是静态风险，尚未在本次文档工作中运行专门复现。

## 16. 媒体执行、恢复与费用

### 16.1 媒体 Provider 与 Runner 分开

Provider 是实际生成服务：demo、manual、Dreamina、OpenAI 图片、Generic HTTP、ComfyUI 等。Runner 是如何执行已经编译的任务：默认 trusted subprocess；pi-agent／codex 等第三方 Runner 默认未启用，需要当前配置对应资格报告。

文字 Codex provider 的持久创作会话与 `runner=codex` 的执行 Agent 是两条不同路线，不能混为“所有步骤都让 Codex 自由操作”。第三方隔离支持显式 docker 或已资格验证的 host，工作目录本身不是安全沙箱。

### 16.2 TaskSpec

任务声明 taskId、renderKey、role、stage、task、objective、inputs、tools、workdir、acceptance、limits 和 reportSchema。工具白名单主要为 render、ffmpeg、read_task、write_report；operator 限制在制作／测试阶段。

执行输入只复制获准参考到任务目录。输出需要真实文件、字节／扩展名验收、实际使用提示词和报告。执行器若改写了 prompt，必须保留冻结身份串，实际结果另建 actualKey 和 requestedKey 重定向，并产生 curator 项供检查。

### 16.3 Dreamina 恢复

```text
费用计划已确认
→ 保存执行输入／attempt 工作目录
→ 提交前记录 submitting
→ CLI 返回可靠 submit_id 后立即持久化
→ query_result 查询原任务
→ 下载文件 → 注册文件与哈希 → 审片

超时／下载失败：持有 submit_id → 查询或下载原任务
提交后没可靠 ID：state_unknown → 人工核对，禁止盲目重提
本地取消：停止本地等待，远端可能仍运行／计费
```

本地执行记录、远端回执和原始媒体保留；恢复应先校验原任务依据。当前有 `runner-runs/{id}/recover` 路由，而通用 Jobs resume 主要恢复文字任务，不应直接重跑付费媒体。

**当前入口存在已确认的代码连接缺陷：** `production.py` 中 `recover_remote()` 位于 `asset_render()` 的函数体内，不是 `ProductionService` 的类方法；`main.py` 路由却调用 `b.recover_remote(...)`。AST 检查已确认该嵌套关系，因此不能将此路由报告为已可用的端到端恢复。底层 Dreamina 原任务查询逻辑存在，但平台恢复入口必须修复并新增路由级回归。

此机制不能承诺供应商端 exactly-once；网络断在提交成功与保存 ID 之间时，当前正确策略是保持未知并核对。其他媒体 Provider 的恢复语义可能不同，必须分别验收。

### 16.4 费用预览

dry-run 返回任务、真实参考、预计时长、缓存、已知／未知价格、阻塞原因和 planHash。执行前核对最新计划；生成中逐任务核对设计与参考。连续失败可触发场次熔断，需要检查后复位。

显示的 estimate 来源于配置，不应假装来自供应商实时账单。恢复原任务的下载与重新提交新候选要在界面上清楚区分。

## 17. 真实媒体审片、采用与制作包

### 17.1 分层审查

| 层 | 方法 | 能力边界 |
|---|---|---|
| 文件与基本参数 | 解码、FFprobe／FFmpeg、尺寸、画幅、时长 | 证明文件可用，不能证明故事正确 |
| 图像粗筛 | 单色／空白、亮度变化、可选 OpenCV 人脸数量 | 正脸数量不是人物身份；亮度不是完整时序 |
| 专用检测器 | 可配置插件的 identity/anatomy/text/temporal/audio 等 | 未配置或不可用返回 unknown |
| 视觉模型 | 真实多个时间点图像检查 informationPayload | 抽帧最多约 5 个点，不能覆盖全部动作／声音 |
| 人工终选 | 真正观看，记录理由、区间和末态 | 仍是当前精品交付关键环节 |

gate 状态包括 pass/fail/review/unknown。任何 fail 导致 rejected；unknown 或 review 保持待复核，不能伪装成自动通过。自带对白有独立 `dialogue_audio` 未知状态，存在音轨不等于台词交付准确。

当前 vision 自动调用条件还要求 model 和 baseUrl；因此纯 codex_cli vision 配置可能被该旧门槛跳过，需专门评估。接入接口存在不等于所有视觉模式已可用。

### 17.2 视频采用

采用记录保存真实文件 SHA-256、实际时长、`interval.in/out`、可解码首尾证据帧与时间、末态观察和依据。结束帧来自采用区间，不能默认为原视频文件最后一帧。

用户修改采用区间或替换上游素材后，根据强依赖图标记后续失效。证据帧与用户／检测器末态观察分别表达；抽到末帧不自动证明所有实体状态正确。

### 17.3 制作包

`ProductionPackage-v1` ZIP 包含 `production-package.json`、可读文档、采用媒体与必要参考、镜头顺序、对白／声音提示、身份／变体对应、来源映射、采用区间、版本和 missing 列表。

包可独立读取；缺失文件列在 missing。具有 missing 的包不能默认称为完整成片交付。外部剪辑按区间使用原视频，最终配音、字幕和剪辑仍由用户在外部工具完成。

## 18. 反馈、经验与持续改进

### 18.1 当前已实现机制

反馈可绑定目标、文本选择、时间点与版本。分类为 fact、preference、production、false_positive。明确且具体反馈可以立即形成当前作品 active 经验；推测偏好和“不好看”等模糊反馈保留 candidate，等待确认／具体化。

经验保存 rule、action、exceptions、conditions、scope、feedbackIds、portableExample、revision、status 和时间。作用范围为 project、genre、global。跨作品推广通过 confirm；默认不把作品人物和道具事实当作通用审美。

使用时按条件等值匹配，并按范围优先级截取，默认最多 8 条（接口上限 20），加入相关创作上下文。生成后保存 experience_application，验证结果包含 resolved、recurred、misapplied、unknown。误用，或因规则／范围不清导致复发，可降回 candidate。

### 18.2 当前能力不是自动训练

```text
反馈 → 具体规则／待确认建议 → 范围匹配 → 下一任务上下文
→ 保存使用记录 → 记录真实验证 → 修改／缩小／停用
```

它不修改模型权重，也不承诺纠正一次永久不犯。当前规则筛选是等值条件加排序，不是语义相似检索；规则过多时可能挤掉相关经验。

采用行为会形成 preference_signal，避免把“采用一版”解释为认可全部细节。代码已记录信号，但本次未看到完整的自动信号提炼、集中建议生成和逐条生成后自动验证服务；`validate` 主要由明确接口提交观察结果。故不能把当前状态称为完全自动自我进化闭环。

### 18.3 跨 A/B 经验交换

`ExperiencePack-v1` 导出 active 的 genre/global 规则，含可携带方法、范例、origin、portableKey 和指纹；导入保存本地副本及回执。项目即使离开外部包仍可读取保存规则。

本次代码中可见的是显式包导入／导出，未确认已经存在自动同步的本地版本化经验文件库。导入会将合法包中的规则设为 active，需评估导入确认和事实外泄边界；修改原规则也不会自动证明另一平台副本已同步停用。

### 18.4 有效性指标

经验页统计已记录的应用和验证、复发率、误用率及每经验结果。unknown 不算成功或失败。这些指标依赖真实验证样本，缺少分母、关联目标不准确或只收集失败反馈时会有偏差。

外部应评估应用与目标版本绑定、经验选择记录、规则冲突、撤销在原会话中的删除同步、自动回归案例生成、合理例外和跨平台传播。这些比增加一个“学习 Agent”名称更能证明改进。

## 19. 安全、恢复、兼容与运行边界

本机 HTTP 检查 Host 和 Origin，写请求要求 `X-Studio-Client: local-ui`；静态资源有 CSP；路径需要保持在允许数据根内。请求标记不是公网用户认证，不可直接把当前服务暴露成多租户平台。

Codex 文字会话禁用 shell、浏览器、媒体生成、应用插件、技能发现、记忆和多 Agent 委派，使用 read-only sandbox 与 JSON 输出约束。作品内容和经验作为数据，不得扩展工具权限。

配置可保存 API 密钥，HTTP 返回做脱敏；本地 settings.json 不能自动视为操作系统加密凭据库。LLM run 可能保存来源与提示上下文，项目备份也可能包含正文及调用记录，分享前需检查。

Store 使用事务、乐观版本和只追加审计；Jobs 启动时把 queued/running 改为 interrupted，文字恢复复用稳定任务和有效结果。由此要求一个数据目录避免同时启动多个服务实例：第二实例初始化可能改写第一实例任务状态。

之前测试导入默认应用触碰生产 Jobs 的问题已通过测试启动前设置临时 STUDIO_DATA 修复；这说明测试通过次数不能替代生产数据隔离设计。服务启动的实例所有权仍值得独立加锁与验收。

旧 SceneExport、新旧 B 路径、历史候选／媒体和备份恢复需要继续兼容。备份恢复建立新项目并重映射 ID，不直接覆盖原项目。未来补充分支与经验库应使用版本化迁移和回滚案例。

## 22. 评估验收场景与建议输出

评审必须围绕精品质量、费用、稳定性和少操作同时判断。建议以相同文本、相同模型配置和固定范围作对照，不仅比较 Agent 数量。

### 22.1 必须包含的业务场景

- 上传 80 万字全本，只选择前 1–5 章：没有隐藏全本调用，进度说明准确，返回完整候选。
- 一段已采用故事分别生成电影和短剧：节奏与观看设计有差异，事实不变，拍摄稿和制作对象不串用。
- 开盒取物、道具交接、盒中物随盒移动、服装／伤势、隐藏／未知／空／销毁：文字账本、参考和真实媒体一致。
- 预演／倒叙回切：播放顺序不改变物理时间，知情和对白不重复交付。
- 只改两个不连续镜头：其他镜头不变，强依赖明确更新，局部节奏调整有适当入口。
- 替换上游视频、修改采用区间：只影响真实依赖，文件末帧不冒充采用末态。
- 一项明确经验、一个合理例外、一项撤销规则：相关任务生效，无关方向不被污染，原会话继续使用。
- 超时／崩溃／提交状态不明／下载失败：保留回执，不盲重提、不重复计费、不误标通过。
- 桌面和窄屏完成阅读、比较、反馈、局部修改、批次确认和制作包独立打开。

### 22.2 需要分别报告的结果

| 类别 | 记录方式 |
|---|---|
| 工程正确性 | 复现输入、版本、状态、预期／实际、测试证据 |
| 文字精品质量 | 盲评来源忠实、人物、因果、影视化差异、首轮采用和返工 |
| 真实媒体 | 看过的文件／时间点、动作／状态／身份／对白、失败样本 |
| 学习有效性 | 规则选中、版本、落实、复发／误用／未知与合理例外 |
| 费用和体验 | 真实调用次数／用量、等待、缓存、费用确认、用户必要点击 |

外部优化建议应给出问题证据、数据模型／接口／Agent 分工变化、缓存和迁移影响、用户操作变化、调用成本变化、兼容方案与可验收场景。完整评审要求和可复制提示词见 `03-外部评估任务书.md`。
